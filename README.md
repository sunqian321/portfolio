# 孙茜 · 作品集（网页版）

把 `孙茜-作品集.pdf`（19 页）做成的可分享网页。设计稿原样呈现，外面套了一层真正的网页外壳：
固定章节导航、滚动进度、封面解锁动效、点击放大看细节、手机端适配。

**每张图导出三档宽度（1440 / 1920 / 2880），浏览器按自己的屏幕挑一档**——
手机下 1440 档（省流量、解码快），Retina 笔记本下 2880 档（不糊）。
配合按章节懒加载，**首屏只加载 202 KB**，滚到哪才下哪。

## 改了设计稿之后怎么更新

1. 把新导出的 PDF 覆盖到 `全作品集/pdf/9.20/孙茜-作品集.pdf`（或改脚本里的 `SRC_PDF` 路径）
2. 重跑导出（约 80 秒，会先清空旧图重建。慢在三档 WebP 编码，`method=6` 是拿时间换体积）：

```bash
python3 tools/build_tiles.py
```

3. 如果**页数或页面顺序变了**，还要同步改 `tools/build_tiles.py` 里的 `PAGES` 表——
   它规定了「第几页属于哪个章节、哪几页单独成图、哪几页进长图序列」。
4. 本地看过没问题，再提交推送（见下）。

### 想调画质或体积

改 `tools/build_tiles.py` 顶部参数后重跑：

| 参数 | 现在 | 说明 |
|---|---|---|
| `MASTER_SCALE` | `1.5` | 母版 2880px 宽。**不能低于 1.5**——Retina 屏（1440 CSS px × 2 倍像素）要的就是 2880px，母版更小的话浏览器只能靠插值放大，画面发糊 |
| `TIER_WIDTHS` | `[1440,1920,2880]` | 导出三档，浏览器自己挑。加档位 = 加仓库体积，一般不用动 |
| `WEBP_QUALITY` | `80` | UI 界面小字多，q76 会把笔画压糊，别再往下降 |
| `TILE_H` | `3000` | 切片高度（母版像素）。2880×3000 = 8.6M 像素，远低于 iOS Safari 约 16M 的解码上限 |

改完重跑，脚本会先清空 `assets/img/` 再重建，**仓库图片总量 39.4 MB**，分布：

| 档位 | 体积 | 谁在用 |
|---|---|---|
| 1440 | 7.9 MB | 手机、普通笔记本 |
| 1920 | 11.6 MB | 1080p 台式 |
| 2880 | 19.8 MB | Retina 屏 ← 真正清晰的这档 |

> 也测过 AVIF：同样的观感只小 8%，不值得多维护一套文件，故未采用。

## 为什么锚点跳转不是「平滑滚动」

整页十万像素高（桌面端 `scrollHeight` 约 106,000px）。如果按常规写
`html { scroll-behavior: smooth }`，点一次导航「联系我」会变成**横穿全页、
持续约 60 秒的动画**，沿途还要把 58 张图、11 MB 全部下载解码一遍。
实测过这个数字，弱显卡的 Windows 上就是一路卡过去。

所以 `main.js` 的 `goTo()` 按距离分流：

| 距离 | 行为 |
|---|---|
| ≤ 2 屏 | 平滑滚动（60fps 动画只要几百毫秒，观感好） |
| > 2 屏 | 直接瞬移（0.33 秒到位，沿途图片根本不触发下载） |

`prefers-reduced-motion` 的用户一律瞬移。

## 性能上的几处刻意取舍

这些改动都是为了弱显卡机器（尤其 Windows 核显），在本机强 GPU 上几乎看不出差别，
所以在弱机器上出问题前不容易发现。改之前先看一眼：

| 位置 | 做法 | 原因 |
|---|---|---|
| `.nav` | 用不透明深色底，**不用 `backdrop-filter`** | 毛玻璃滚动时每帧都要重新采样背后的画面，是滚动卡顿的常见来源 |
| `.progress` | `transform: scaleX()`，**不用 `width`** | `width` 每帧触发布局+重绘；`transform` 只走合成层 |
| `.unlock-ring::after` | 脉冲动画只动 `transform`/`opacity` | 原来直接动画 `box-shadow`，每帧重绘且 `infinite` 永不停止 |
| `main.js` 的 `measure()` | 缓存 `offsetTop` / `scrollHeight` | 读这些属性会强制同步布局。以前放在每帧的 `update()` 里，等于每帧重新布局一次。现在只在 `resize` 和 `ResizeObserver` 触发时重量 |

> 顺带一提：右侧那排章节圆点（`.rail`）已按用户要求移除，它是固定定位 + 毛玻璃，
> 既挡视线也在滚动时要额外合成。

## 已知限制

- **图中的文字不能选中、不能复制、搜索引擎读不到**。因为整站是设计稿导出的图片。
  如果需要可搜可复制，得把页面改写成真正的 HTML 排版，那是另一套做法。
- **国内访问速度不稳定**。GitHub Pages 服务器在海外。免费又国内快的方案在 2026 年基本不存在
  （Gitee Pages 已停服；腾讯云 EdgeOne 国内节点需 ICP 备案，7–20 个工作日）。
  缓解手段是首屏压到 202 KB、每张图按屏幕挑档位、按章节懒加载。
- **仓库 39.4 MB**（2026-09 从 9.7 MB 提上来的）。之前只导 1920 一档，Retina 屏上必然发糊；
  现在每张图存三档，其中 2880 档独占 19.8 MB。真正下载到单个访问者机器上的只有其中一档
  （手机 1440 那 7.9 MB 里的若干张）。

  **但这 39.4 MB 不是「打开卡」的原因**——实测过一次访问最多只下 1～2 MB。真凶是每帧的
  计算量，见上面「性能上的几处刻意取舍」。

  真要压体积，只有三条路，每条都有明确代价：
  | 做法 | 省 | 代价 |
  |---|---|---|
  | 去掉 2880 档 | 19.8 MB | Retina Mac 退回 1920，**发糊**（就是最初那个问题） |
  | 去掉 1920 档 | 11.6 MB | 1080p 台式退回 1440，**发糊**（Windows 大多数是这种屏） |
  | 换 AVIF | 约 30% | 解码更慢，**弱机器更卡**，方向反了 |

  画质和体积在这条路上是直接对冲的，没有免费午餐。
- **手机端**：16:9 的画面在手机屏幕上会缩小，字看不清。点一下画面可以全屏放大、双指缩放。
- **不含 PDF 下载**。原 PDF 有 39MB，放进仓库会让每次推送都多传 39MB，且以后每换一版
  都会在 git 历史里永久留一份。现已从仓库排除（`.gitignore` 里已屏蔽），
  文件仍留在本地目录里。若以后确实需要，建议放网盘、把链接加到联系区。
